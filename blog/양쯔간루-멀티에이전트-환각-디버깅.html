핵심 요약
  1. 대장 에이전트가 검색 에이전트와 레시피 에이전트를 병렬로 호출했고, 레시피 에이전트는 아무 배경 정보 없이 낯선 트렌드 용어를 받았다.
  2. 레시피 에이전트는 모른다고 말하는 대신 그럴듯한 특징을 지어내서 배합비를 완성했다 — 검색 결과가 화면에 함께 떠 있었는데도.
  3. 해법은 "검색을 먼저 시키자"가 아니라 "모르는 걸 모른다고 말할 수밖에 없게 만들자"였다. tool 스키마, 오케스트레이터 프롬프트, 하위 에이전트 프롬프트 세 군데에 각각 다른 방어선을 심었다.

01시스템 구조

풀무원 신제품 아이디어를 위해 만든 시스템은 세 개의 AgentCore harness로 구성된다. 대장 에이전트는 직접 아무 일도 하지 않고, 두 하위 에이전트에게 위임만 한다.

orchestrator_harnesstool 2개, 직접 추론 없음
call_recipe_agentLambda → InvokeHarness
recipe_researcher_harness내부 배합비 DB 검색
call_web_search_agentLambda → InvokeHarness
web_search_harness_tavily_krTavily 웹 검색

두 하위 에이전트는 서로의 존재를 모른다. 정보가 오가려면 오케스트레이터가 직접 중계해야 한다.

02증상: 절반만 맞는 답변

테스트 프롬프트는 일부러 고른 것이었다 — "양쯔간루", 2026년 상반기에 SNS에서 갑자기 유행한 홍콩식 망고·포멜로·코코넛밀크 디저트. 학습 데이터에 온전히 반영됐을 가능성이 낮은, 환각을 유도하기 좋은 키워드다.

"양쯔간루를 조사하고 신제품을 제안해줘"라는 요청에 오케스트레이터는 두 tool을 사실상 동시에 호출했다.

recipe_researcher_harness가 받은 입력 근거 없음
call_recipe_agent(
  query: "양쯔간루 배합비 짜줘"
)
web_search_harness가 받은 입력 정확
call_web_search_agent(
  query: "양쯔간루 뜻 유래 소개"
)

검색 에이전트는 제대로 일했다. 1984년 홍콩 레이가든에서 만든 디저트, 망고·코코넛밀크·사고펄·포멜로 구성이라는 정확한 정보를 가져왔다. 문제는 레시피 에이전트였다 — query 하나 말고는 아무것도 받지 못한 채, "양쯔간루"라는 이름만으로 배합비를 만들어야 했다.

최종 답변 (신규 배합비 제안 부분) 환각
레시피 에이전트는 "양쯔간루"를 자기 지식 안에서 그럴듯한 매운 소스·양념류로 오해하고, 실제로는 존재하지 않는 특징(매운맛, 발효 베이스 등)을 근거로 원재료 배합비를 새로 지어냈다. 검색 결과창에는 정답이 떠 있었지만, 레시피 에이전트는 그 결과를 본 적이 없었다.

03원인: 세 가지가 동시에 어긋났다

1) 병렬 tool call에는 데이터가 흐르지 않는다

Claude 같은 모델이 한 턴에서 tool_use 블록 두 개를 동시에 내보내면, 그 둘은 서로의 결과를 알 수 없는 상태로 계획된다. 오케스트레이터가 call_recipe_agent와 call_web_search_agent를 같은 턴에 호출했다는 건, 레시피 쪽 문구를 쓰는 시점에 검색 결과가 아직 존재하지 않았다는 뜻이다. "먼저 검색하라"는 규칙이 없으면 병렬 호출이 기본값이 된다 — 그게 더 빠르니까.

2) tool 시그니처에 "이미 아는 것"을 실을 자리가 없었다

기존 call_recipe_agent는 query 하나만 받았다. 오케스트레이터가 검색 결과를 나중에 알게 되더라도, 그걸 레시피 에이전트에게 넘길 파라미터 자체가 없었던 것이다.

3) 하위 에이전트는 확신하도록 설계돼 있었다

레시피 에이전트의 원래 프롬프트는 "사용자가 방향을 정하면 빠르게 배합비로 넘어가라"고만 되어 있었다. 낯선 용어를 만났을 때 "모른다"고 말할 수 있는 명시적 permission이 없었다 — 그리고 언어모델의 기본값은 침묵이 아니라 그럴듯한 답이다.

04왜 뻔한 해법 두 개는 부족했나

✕
"무조건 검색부터 시키자"

모든 배합비 요청 앞에 검색을 강제하면, "저당 사과주스"처럼 모델이 이미 정확히 아는 흔한 카테고리에도 매번 레이턴시와 비용이 붙는다. 이 시스템이 실제로 자주 받을 요청의 다수는 일반 식품 카테고리다 — 그 경로를 느리게 만드는 건 손해다.

✕
"모델의 판단에 맡기자"

이게 바로 이번 버그의 원인이었다. 모델은 "양쯔간루"가 낯설다는 걸 스스로 감지하지 못했다 — 오히려 확신을 갖고 틀린 답을 냈다. "네가 모르는 걸 판단해서 검색해라"는 지시는, 판단 능력 자체가 고장 난 지점을 다시 그 판단에 맡기는 순환 논리다.

필요한 건 "검색 여부"를 모델의 자기 확신에 맡기지 않는 것이다. 대신 정보가 실제로 흘러갈 수 있는 구조를 만들고, 확신을 표현하려면 근거를 대야 하는 상황을 강제하는 쪽으로 방향을 바꿨다.

05해법: 3중 방어선

세 군데 중 하나만 고쳤다면 다음 트렌드 용어에서 똑같이 무너졌을 것이다. 그래서 서로 독립적으로 작동하는 방어선을 세 겹 심었다.

1
tool 스키마에 context 필수 필드 추가

빈 깡통을 채우라고 요구하면, 채울 근거가 없다는 사실이 모델 눈에도 보인다.

call_recipe_agent inputSchema (발췌)
{
  "query": { "type": "string" },
  "context": {
    "type": "string",
    "description": "이 제품/용어에 대해 알려진
      배경 정보. 정보가 없으면
      '사전 정보 없음'이라고 명시."
  }
},
"required": ["query", "context"]

단독으로는 못 막는다 — 병렬 호출 시 모델이 context에 지어낸 내용을 채워 넣을 수도 있다. 그래서 아래 2번과 반드시 짝지어야 한다.

2
오케스트레이터: 순차 호출을 명시적 규칙으로

"고유 명칭·트렌드 용어"를 감지하는 규칙과, 그 경우 검색을 단독으로 먼저 호출하라는 규칙을 시스템 프롬프트에 박아 넣었다.

orchestrator_harness 시스템 프롬프트 (발췌)
고유 명칭·트렌드 용어 처리 (환각 방지) 1. 절대 그 용어의 의미를 스스로 추측하지 마세요. 2. call_web_search_agent를 단독으로 먼저 호출하세요 (call_recipe_agent와 동시에 호출 금지 - 병렬 호출 금지). 3. 검색 결과를 받은 이후에 call_recipe_agent를 호출하되, context 파라미터에 검색 결과 요약을 반드시 포함하세요. 4. 일반적으로 잘 알려진 카테고리는 검색 없이 바로 호출해도 됩니다.
3
레시피 에이전트: 모른다고 말할 권한 부여

오케스트레이터가 규칙을 놓치는 경우에 대비한 최후 방어선. 이건 라우팅과 무관하게 항상 작동한다.

recipe_researcher_harness 시스템 프롬프트 (발췌)
모르는 용어·트렌드 제품 처리 (환각 방지) [배경 정보] 없이 낯선 고유 명칭이 왔고 스스로 확신할 수 없다면: - 배합비를 절대 추측해서 만들지 마세요. - "'[용어]'가 정확히 어떤 제품인지 설명해주시거나, 시장조사 결과를 알려주시면 그것을 기반으로 배합비를 제안하겠습니다"라고 되물으세요. - 확신이 서지 않는데 아는 척하는 것이 틀린 정보를 주는 것보다 항상 더 위험한 실수입니다.

06검증: 같은 질문, 다른 순서

같은 "양쯔간루" 프롬프트를 다시 넣었다. 이번엔 tool 호출 순서 자체가 달라졌다.

수정 후 tool 호출 로그 순차 실행
1  call_web_search_agent(query: "양쯔간루...")
2  call_web_search_agent(query: "양쯔간루...")   ← 재시도
3  call_recipe_agent(
     query: "양쯔간루를 활용한 신제품 배합비",
     context: "1984년 홍콩 레이가든에서 개발된
       디저트. 망고, 코코넛밀크, 사고펄,
       포멜로(자몽류)로 구성..."
   )

레시피 에이전트가 마침내 받은 context는 정확했고, 그 결과 최종 제안 세 가지 — 떠먹는 디저트, RTD 음료, 비건 볼 — 모두 실제 양쯔간루의 구성 요소(망고·코코넛·포멜로·사고펄)를 정확히 반영했다. 검색 파트와 배합비 파트가 처음으로 같은 사실 위에서 있었다.

07일반화되는 교훈

tool signature는 "무엇을 시키는가"뿐 아니라 "무엇을 이미 아는가"도 실어야 한다

query 하나로 끝나는 tool은 편해 보이지만, 에이전트 사이에 사실이 전달될 통로 자체를 막아버린다. 근거를 담을 필드가 없으면, 모델은 근거 없이 답한다.

병렬 tool call은 "서로 독립적"이라는 가정을 암묵적으로 강제한다

속도를 위해 병렬 호출은 기본값으로 두되, 실제로 의존 관계가 있는 호출은 예외로 명시해야 한다. 이 예외를 모델의 판단에 맡기면, 모델이 오판하는 바로 그 지점에서 시스템도 함께 무너진다.

"모른다"는 답도 permission이 필요하다

언어모델의 기본 동작은 침묵이 아니라 그럴듯한 문장이다. 불확실성을 인정하는 것이 시스템 프롬프트에 명시적으로 허용되지 않으면, 모델은 거의 항상 아는 척을 택한다.

세 가지 방어선 중 어느 하나도 완벽하지 않다. tool 스키마는 병렬 호출 자체를 막지 못하고, 프롬프트 규칙은 지시일 뿐 보장이 아니고, 사후 방어선은 이미 잘못된 요청을 받은 뒤의 최소한의 안전장치다. 그래도 세 겹을 겹치면, 하나가 새는 지점을 다른 하나가 잡아준다 — 지금까지는.
